## Context

A file that landed is not a data product. Eligibility extracts and encounter batches feed silver, gold, and outbound files that other systems treat as fact. The failure mode is a pipeline gate that checks a box in the orchestrator while consumers read the base table, including rows that failed a contract.

The operating requirement is a released view. One manifest version carries the units that may be read and the row sequences that are quarantined. The pointer flips last. A lag leaves the previous version in place, so a delay cannot reveal a quarantined row.

The full brief, including the architecture figure and the trade-offs, is the [DQ Control showcase](/demos/dq-control). The sandbox below is the same gate.

## Architectural Approach

The control plane decides. The data plane computes. Checks for completeness, validity, uniqueness, referential integrity, and hop balance run where the rows live, and only counts, rates, and dispositions come back.

Dispositions have a total order. The worst one selects the policy mode for the authority. Floors then raise it: a failing check is never autonomous, and an unbalanced hop requires two people. An autonomy tier is a ceiling on top of that. L4 may release a pass. L2 and L1 hold the unit. A missing tier is treated as L1.

Basic checks start advisory. A warning is recorded and the mode stays where a pass would have left it. A two-person promotion makes the same check gating, which is when a soft null-rate breach can quarantine rows and a broken member reference can reject the unit.

## Governance & Guardrails

Remediation proposes a closed verb and a dry-run: release, quarantine rows, reject, or hold. It does not rewrite the landed file. Human release binds the decision to the fingerprint and the quarantine set. The highest mode adds a second person and a step-up. The verifier is a separate identity. Publish waits on its attestation.

An advisory model may comment on a card. The mode function does not read that comment.
